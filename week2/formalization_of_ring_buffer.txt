PART (a): HAPPENS-BEFORE AND DATA RACES

Model an execution as a set of memory events.

1. Program order

If event e occurs before event f in the same thread, then:

e ->po f

Program order only orders events within one thread.

2. Synchronizes-with

If one thread performs a release operation on an atomic object, and another thread performs an acquire operation on the same atomic object and reads the value written by that release, then:

release write ->sw acquire read

This is the mechanism that creates ordering between threads.

3. Happens-before

Happens-before is generated by:

- program order;
- synchronizes-with;
- transitivity.

Thus, if:

e ->po f
f ->sw g
g ->po h

then:

e ->hb h

4. Conflicting actions

Two actions conflict when:

- they access the same memory location;
- they occur in different threads;
- at least one action is a write.

5. Data race

A data race occurs when two conflicting non-atomic actions are not ordered in either direction by happens-before.

That is, neither:

e ->hb f

nor:

f ->hb e

holds.

In C and C++, a data race causes undefined behavior.

Important distinction:

Race freedom does not imply queue correctness. An algorithm may use atomics everywhere and still be logically incorrect because it lacks the ordering needed to preserve its invariant.


PART (b): MPSC RING BUFFER INVARIANT AND CORRECTNESS

Queue structure

Let:

H = head
T = tail
N = buffer capacity

Both H and T are monotone logical counters.

Logical position k uses physical slot:

k mod N

Each slot contains:

- a payload;
- a sequence or generation marker.

The marker for logical position k is specific to k, for example k+1. This prevents the consumer from confusing position k with an older or later use of the same physical slot.

Position lifecycle

Each logical position moves through:

unclaimed -> claimed -> published -> consumed

- Claimed: one producer successfully advances T from k to k+1.
- Published: that producer writes the payload and then publishes the slot marker.
- Consumed: the consumer reads the payload and advances H from k to k+1.

Buffer invariant

At every reachable state:

0 <= H <= T

and:

T - H <= N

Also:

1. Every position k < T has been claimed exactly once.
2. Every position k < H has been consumed exactly once.
3. Every position H <= k < T is either:
   - claimed but not yet published; or
   - published but not yet consumed.
4. If k is published, slot k mod N contains the payload for k and the marker identifying generation k.
5. Distinct live logical positions occupy distinct physical slots.

Why distinct live positions use different slots

If two live positions k1 and k2 mapped to the same physical slot, then their difference would be at least N.

But all live positions lie inside the interval [H,T), whose length is at most N.

Therefore two different live positions cannot occupy the same physical slot.

Unique claim

To claim position k, a producer must successfully perform the atomic transition:

T: k -> k+1

CAS is atomic, so only one producer can succeed.

Since T is monotone, it never returns to k.

Therefore each logical position is claimed at most once.

Correct payload visibility

The producer performs:

write payload k
->
release-publish marker for k

The consumer performs:

acquire-read marker for k
->
read payload k

The release publication synchronizes with the acquire read.

Therefore:

producer payload write
happens-before
consumer payload read

The marker identifies which logical generation is ready. The release/acquire pair guarantees visibility of that generation's payload.

Unique consumption

To consume position k, the single consumer must advance:

H: k -> k+1

Since H is monotone and there is only one consumer, this transition can happen only once.

Therefore each logical position is consumed at most once.

Safe slot reuse

Positions k and k+N use the same physical slot.

The slot must not be overwritten for k+N until the consumer has finished reading k.

The intended event chain is:

consumer reads old payload k
->
consumer release-stores advanced H
->
future producer acquire-reads advanced H
->
future producer writes payload k+N

Therefore:

consumer read of old payload
happens-before
future producer overwrite

No duplicate

Suppose an item from logical position k is returned twice.

That would require position k to be consumed twice.

But H advances through k only once.

Contradiction.

Therefore each enqueued item is returned at most once.

No drop

After a successful enqueue completes, the item is always in exactly one of two places:

- still represented by its unique published slot; or
- already represented by one completed dequeue.

The physical slot cannot be reused until the consumer advances beyond that position.

Therefore the item cannot disappear before being consumed.

This is the safety form of no-drop.

The stronger claim that every item is eventually consumed requires progress assumptions:

- the consumer keeps running;
- every producer that claims a position eventually publishes;
- the scheduler does not permanently starve the relevant threads.


PART (c): WHICH OPERATIONS MAY BE RELAXED?

Relaxed means:

- the operation remains atomic;
- it remains indivisible;
- the atomic object still has a coherent modification order;
- but the operation creates no cross-thread synchronizes-with edge for surrounding memory accesses.

1. Producer tail CAS

Conclusion: may remain relaxed.

Reason:

The CAS is used only to assign a unique logical position.

Relaxed CAS still guarantees atomicity and unique claiming.

It does not need to publish payload data.

2. Producer slot publication

Conclusion: cannot be relaxed.

Required ordering:

write payload
->
release-publish marker

If the publication is relaxed, the consumer may observe the marker without the memory model guaranteeing visibility of the earlier payload write.

The proof loses:

producer payload write
happens-before
consumer payload read

3. Consumer slot-marker read

Conclusion: cannot be relaxed.

Even if the producer uses a release store, a relaxed consumer load does not acquire it.

Therefore no synchronizes-with edge is formed.

Again, the proof loses:

producer payload write
happens-before
consumer payload read

4. Consumer head store

Conclusion: cannot be relaxed in this design.

Required ordering:

consumer reads old payload
->
consumer release-stores advanced H
->
future producer acquire-reads H
->
future producer overwrites reused slot

If the consumer's head store is relaxed, a future producer may observe that the slot is free without being ordered after the consumer's old payload read.

The producer may then overwrite the physical slot too early.

Final classification

Producer tail CAS:
relaxed is safe.

Producer slot publication:
must be release.

Consumer slot-marker read:
must be acquire.

Consumer head store:
must be release.

The corresponding producer read of H must be acquire.

Core lesson

Provably wrong, TSan-detectable, and visibly failing on a particular CPU are three different things.

An ordering can be required by the C++ memory model even if the M4 rarely or never exposes the bad execution during testing.
